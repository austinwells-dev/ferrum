# Ferrum architecture

How Ferrum fits together today. How it got here, phase by phase, including the original runtime design, is in [history/](history/) ([runtime internals by phase](history/architecture-by-phase.md), [journals](README.md#engineering-journals)).

## Overview

Ferrum is a single Rust crate with two inference engines that share one Metal backend.

| Layer | Modules | Role |
|---|---|---|
| Front ends | `src/bin/ferrum-tui`, `ferrum-cli`, `ferrum-server` | TUI, terminal chat, OpenAI/Anthropic HTTP server |
| Chat runtime | `hybrid::runtime`, `hybrid::chat` | GGUF chat templates, streaming split into reasoning / content / tool calls |
| Large-model engine | `hybrid::{plan, engine, session, weights, draft, mtp, speculative}` | Qwen3.5-family hybrids: memory planning, forward pass, sessions, speculative decoding |
| General engine | `model`, `nn`, `ops`, `generation`, `sampling`, `quantization`, `metal::legacy` | Dense, MoE and short-conv transformers (Qwen2.5/3, Granite, OLMo 2, LFM2). Behind the `legacy-engine` cargo feature; no front end uses it |
| Vision | `vision` | Qwen3-VL and, experimentally, LFM3-VL still-image encoders that feed the hybrid engine |
| Core | `tensor`, `loader`, `tokenizer` | Tensors, safetensors/GGUF parsing, tokenizers |
| Backend | `metal` (+ `metal/shaders/*.metal`) | Device, pipeline cache, command batching, residency, the only `unsafe` code |
| Oracles | `reference` | CPU implementations used only by the general engine's tests (feature-gated) |

### The hybrid engine

Qwen3.5-family models interleave two kinds of layer. Three of every four layers are **Gated DeltaNet** linear attention, which keeps a fixed-size recurrent state per head. The fourth is **gated full attention** with a KV cache. The engine (`src/hybrid`) has its own kernel library (`hybrid.metal`) and an explicit-geometry dispatch path.

**Experimental:** the `flint` architecture (unsloth's Flint GGUFs; see [experimental.md](experimental.md)) reuses the same engine with different geometry: every layer is full attention with 128-wide heads, learned per-head sinks, sliding windows of 513 on 35 of 49 layers, RoPE on the windowed layers only, dense feed-forward for the first two layers, then 256 sigmoid-routed experts with normalized top-6 weights and an ungated shared expert. Its kernels are the `_d128` variants of the attention kernels; the legacy `h_flash_attn_1/4` and non-staged `h_flash_attn_mpp` paths cover only Qwen-shaped attention and reject the rest. Flint tool calls use `<tool_call>NAME<arg_key>K</arg_key><arg_value>V</arg_value>…</tool_call>`, which the parser reads alongside Qwen's `<function=…>` form and types by the tool's schema.

**Experimental:** `spark2_5` (XHToken's Spark-X2.6) takes the same attention-only path: three 512-token sliding-window layers to each global one, with their own RoPE width and base, fused QKV split at load, no QK norm, a per-head sigmoid output gate (`h_head_gate`) and a GEGLU feed-forward (`h_geglu`). Its chat template uses Flint's tool-call format.

**Experimental:** `lfm3` (LiquidAI's LFM3-1.7B and the LFM3-VL-2B language file; see [experimental.md](experimental.md)) follows the layer kinds in the GGUF rather than a fixed pattern. Both Q4_K_M files have 13 gated short convolutions (kernel 7; the state is the previous 6 `B*x` rows), 5 sliding-window attention layers (window 256, full 128-dim RoPE at base 10,000) and 6 full-attention layers (RoPE base 1,000,000, partial rotation by dividing the angle by `rope_freqs.weight`). The text file's trained context is 262,144; the VL file's is 128,000. Norms are a sandwich: RMSNorm on the branch, the residual add, then the next pre-norm. Attention uses separate Q, K and V, QK RMSNorm, and the same per-head gate as Spark. Draft trees are refused; a chain verify replays accepted `B*x` rows into the conv window. LFM3-VL still images are a separate `lfm3vl` projector ([vision.md](vision.md#lfm3-vl)): `<|image|>` is repeated once per token, and each of those tokens has its own position. `<|video|>` and the audio projectors are refused.

- **Weights** (`weights`) keep their GGML block encoding (Q4_K, Q6_K, IQ4_XS, IQ3_XXS, IQ3_S, IQ2_S, ...) and are read directly into Metal storage. Decode uses per-type GEMV kernels (ports of llama.cpp's `mul_mv` that take F32 activations). Prefill dequantizes weight tiles to F16 and multiplies them on TensorOps with F32 accumulation.
- **Memory planning** (`plan`) predicts every allocation from GGUF metadata before reading a weight: trunk tensors (page-rounded as Metal allocates them), chunk scratch, recurrent state and snapshots, F16 K/V per position, and drafter and vision budgets. With no requested context, it fits the largest one under the GPU working set minus a reserve. A request that can't fit fails before loading and reports the largest context that would. Everything is allocated once, so memory stays flat for the life of the process. Predictions match Metal's measured allocations to within 4 MiB on every validated model (weights plus scratch, and state, measured separately).
- **Forward pass** (`engine`) processes the prompt in fixed-size chunks (`--chunk`, default 512). Attention is flash-style and DeltaNet layers run a recurrent kernel over each chunk, so no activation grows with the square of the sequence length.
- **Sessions** (`session`) hold the state and the tokens it represents. Recurrent state can't be truncated, and a sliding-window layer's K/V ring overwrites its oldest rows, so the session snapshots both (the recurrent state and a copy of every ring) at the end of every prompt, in LRU slots budgeted by the planner. A new request reuses the longest common prefix, restoring the deepest snapshot at or before the point where it diverges; full-attention K/V rows are append-only and stay valid. A model without recurrent state resumes exactly at the divergence, from its rings or from a later snapshot's copy of them. Chat templates rewrite a past reply (dropping its reasoning) once a newer user message follows it, so the next turn diverges where that reply's header starts, a few tokens before the end-of-prompt snapshot. `Runtime::chat_prompt` finds that position (the render without the generation prompt) and the session also snapshots there, pinned when the prompt ends in a user message so the snapshots of later tool rounds don't evict it. [`hybrid_chat_reuse`](../examples/hybrid_chat_reuse.rs) prints how much of each turn a scripted chat reuses. `Session::generate` is `begin` followed by `advance` until done; each `advance` runs one prompt chunk or one decode step (plain or a speculative cycle), and everything one step leaves for the next lives in the session's own state, so a caller can interleave several sessions on one model. The planner's `parallel` multiplies the per-session K/V, recurrent state and snapshots; scratch, drafter and projector are shared.
- **Sampling** applies penalties on the GPU, and a block kernel returns the top 32 logits of every 1,024-token block, so the global top 32 is exact. The host then applies temperature, top-k, min-p and top-p. Greedy decoding keeps an on-GPU argmax.

### Speculative decoding

`HybridModel::verify` runs `[anchor, d1..dk]` as one forward without advancing the state. Attention layers write K/V past the cached length, and rejected rows are simply overwritten later. DeltaNet layers read their state but don't write it, and instead record each row's pre-conv inputs on a small tape. `commit(n)` replays the first `n` tape rows into the live state. That costs one extra read and write of the state per step, compared with roughly 150 MB per row for per-position state copies on the 27B, and a failed verify leaves the session valid.

`verify_tree` checks a draft tree instead: each row sees the cached sequence and only its own ancestors among the new rows (an ancestor bitmask per row), at position `len + depth`, through `_tree` variants of the verify attention kernels and of the DeltaNet conv and delta-rule kernels, in which each node starts from its parent's state. `commit_path(path)` keeps one root-to-node path: it replays that path's tape rows, moves its K/V rows to consecutive positions (F16 or Q8, linear or ring) and moves the captured features to the rows the drafter ingests. The session walks the tree greedily from the anchor, following the child the target picks at each row. The MTP drafter grows trees best first by path probability under a node budget: each MTP pass runs the three likeliest frontier tokens together, each from its parent's hidden state and with tree-masked attention to its own ancestors, so the same `_tree` kernels serve drafting, where a pass's rows sit partway into the tree ([Phase 11 journal](history/phase11-journal.md)).

Drafters (`draft`, `mtp`) read the target's residual stream at a few layers. MTP chains the model's own NextN block. DFlash, DFlash2 and DSpark are block-diffusion drafters loaded from Hugging Face checkpoints and quantized to Q4_0 at load. Verification of 4–32 rows uses a narrow 16×64 TensorOps tile, which brought a 16-row verify on the 27B from 3.5× to about 1.5× the cost of a single-token step (17 rows, a 16-draft block plus its anchor, costs 2.4×). The details are in the [Phase 9 journal](history/phase9-journal.md).

### Front ends

`ferrum-server` runs the model on one thread behind a FIFO queue and gives each connection its own thread, so status endpoints respond during generation. With `--parallel N` the `Runtime` holds N sessions (`session` plus `slots`); tensor and device handles are `!Send`, so the model thread's scheduler (`ferrum-server/worker.rs`) gives every running request one `Runtime::advance` in turn rather than using threads. It routes each request to a slot by explicit `id_slot`, then by prefix shared with the slot's cache, then by cache key, then least recently used. Only slot 0 carries the drafter. `hybrid::chat` renders the GGUF's Jinja template with minijinja configured like Hugging Face's `apply_chat_template`. Plain chat, multi-turn reasoning and tool calls render byte-identically to llama-server's `/apply-template`. The TUI drives the same `Runtime` in-process for chat, the agent and benchmarks, and starts `ferrum-server` as a child process for Serve. Agent commands run under `sandbox-exec` with the profile in `src/bin/ferrum-tui/sandbox.sb`.

### Safety boundary

`src/lib.rs` is `#![deny(unsafe_code)]`, with a single `#[allow]` on the `metal` module. That module has six `unsafe` blocks, each with a `SAFETY:` comment: mapping shared bytes for initialization and for reading completed results, zeroing fresh allocations, a residency-set capacity hint, threadgroup memory length, and encoder binding. Published tensors are immutable; the hybrid engine's persistent buffers (K/V, recurrent state, scratch) change only as checked kernel outputs. No output aliases an input or another output, and command-buffer completion is checked before any result can be mapped. Tensor and device handles use `Rc`, so they are `!Send` and `!Sync`. Outside the library, the server has one `unsafe` call: a non-blocking one-byte `recv` peek that notices when a client disconnects.

### Core runtime

Both engines sit on the same Metal backend (`src/metal/mod.rs`); the general engine adds its own dispatcher and kernel switches in `metal/legacy.rs`.

- **Tensors** (`tensor`) hold an `Rc<MetalBuffer>`, a byte offset, a shape, a row-major layout and a dtype (F32, F16 or BF16; accumulation is F32). Reshape shares storage, and views are checked contiguous subranges; there are no arbitrary strides. Quantized weights live in `PackedStorage`, which is raw bytes with no dtype.
- **Storage** is `StorageModeShared`, zero-initialized on allocation, at least 4 bytes long. The CPU reads and writes it through scoped closures, so no mapped slice escapes, and there are no staging copies or blits.
- **Pipelines** are compiled at runtime from embedded MSL and cached by source and entry point. Built-in kernels have a separate name-keyed cache: `hybrid.metal` and `hybrid_mlx.metal` for the hybrid engine; `ops.metal` and `project_mpp.metal` for the general engine and the keep-alive kernel.
- **Dispatch.** The hybrid engine calls `dispatch_hybrid` with explicit input and output byte ranges, grid and threadgroup sizes. Before anything is encoded, every binding is checked: it lies inside its allocation, belongs to this device, overlaps no other output and no input of the same dispatch, and doesn't read a range a failed submission wrote.
- **Execution.** Inside an execution scope, kernels are encoded into command buffers of up to `batch_limit` dispatches (1,024 by default). The first buffer of an epoch is committed early, after `FERRUM_EARLY_COMMIT` dispatches (32 by default), so the GPU starts while the CPU encodes the rest. A shared encoder can run kernels concurrently, inserting buffer barriers when byte ranges conflict. Each submission retains every bound buffer until it completes. Each allocation records which byte ranges it wrote and in which epoch, so the CPU can map a range only once every write to that range has completed.
- **Residency.** `MetalDevice::new()` adds weight allocations to a residency set on the queue. A background thread commits an empty kernel every 500 ms for 3 minutes after the last submission, so the weights stay resident across short idle gaps. `MetalDevice::without_keep_alive()` skips the thread.

## Image generation

`src/diffusion` draws images with Qwen-Image-2.1 in stages that never coexist in memory: the Qwen3-VL text encoder (the hybrid engine run as an attention-only model; the layer-35 output before the final norm is the conditioning), a 32-block single-stream transformer with one shared modulation, and a convolutional VAE decoder (implicit-GEMM convolutions on TensorOps).

An edit adds two stages in front. Each condition image goes through Qwen3-VL's vision tower (`vision::VisionModel`, loaded from the encoder's safetensors with its DeepStack mergers), whose rows replace the prompt's image-pad tokens; the language model adds the DeepStack features to those rows after its first layers (`ImageSpan::deepstack`). The image also goes through the VAE's encoder (`vae_encoder.rs`: stride-2 convolutions with averaged space-to-depth shortcuts) into normalised latents.

The transformer reads one sequence: text rows, then each condition image's latents, then the picture being made. Text and condition rows are modulated from `t = 0` and attend block-causally (each block sees itself and what came before; `rope::Layout` places every block and `dit::key_limits` gives each row its last visible key), so their K/V is computed once and each step runs only the picture's rows, which see everything.

`Pipeline` estimates each stage's bytes (the tests hold every stage within 4 MiB of its measured peak), checks them against the working-set limit minus what is already resident, and frees a stage before loading the next. The TUI's `generate_image` tool runs on the chat model's thread: when `Pipeline::fits_now` says the stages do not fit beside the chat model, it drops the model for the picture and loads it again after. The image kernels (`i_*`, `vae_*`) are compiled only with image runs, so LLM startup is unchanged. No `unsafe` was added.

A picture a tool makes, and a file the `view_image` tool reads, reach the model as an image part inside that tool's reply (`role: "tool"` with a content array), beside the text that names the path. They take the same `vision::media::take_images` path as attached images (the template marker is `<|image_pad|>` on Qwen and `<|image|>` on LFM3-VL), so the session's prefix reuse treats them like any other image. A reply that would take a prompt past `MAX_IMAGES` (16) carries only its text, saying why; the same happens when the loaded model has no projector.
